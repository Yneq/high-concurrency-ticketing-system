資料歸誰管？

PostgreSQL 保存庫存、冪等預約、訂單、outbox 與 dead letters。Redis 是可重建快取；Kafka 保存待消費訊息。兩者都不能憑空創造一張 DB 沒保留的票。

三個成功時點

HTTP 202：庫存保留已持久化。Broker ack：訊息被 Kafka 接受。PAID：模擬付款狀態已提交。它們是不同時點，不應混用。

06 / FAILURE & TRUST BOUNDARIES

知道系統守住什麼，也知道限制在哪裡

Redis 壞了會怎樣？快取準確嗎？

連線／命令預設 500ms timeout，失敗回退 DB 的 atomic UPDATE；增加 DB 負擔但不放棄防超賣。週期 5 秒投影、stock TTL 15 秒，與 admission 不是同一交易。快取過高由 DB 擋住，過低可能短暫 409。這版沒有宣稱快取強一致。

Kafka 中斷、Consumer 失敗與 DLQ

未發布事件留在 outbox，恢復後重送。一般 Consumer 有限重試後送 DLT；DLT 自己寫 DB 失敗時無限重試，不反覆轉送自己。毒訊息或未知 reservation 不能憑空建單。DLQ replay 只表示已重新送消息，不表示付款完成。

時間邊界：為什麼用 clock_timestamp？

CURRENT_TIMESTAMP 固定在交易開始時間。付款可能在到期前開始、等待 row lock 後才執行，因此要用拿鎖後的真實 DB 時間檢查 deadline。否則晚到付款可能被誤當仍有效。expiry 的批次掃描則以該輪交易時間找已過期者，晚一輪掃到可以接受。

錯誤回應：400、403、404、409

400：key／user／付款 body 不合法或新版使用活動 1。403：admin token 未通過。404：活動、預約或 DLQ ID 不存在。409：售罄／cache 耗盡、同 key 不同 payload、或訂單仍 QUEUED 不可付款。資料庫／broker 非預期故障仍可能是 5xx，不應算成售罄成功。

安全與生產範圍

目前沒有一般使用者登入、可信 userId 或付款 ownership 驗證；付款只是布林模擬，沒有真實金流／webhook。admin token 是本機示範保護。單機 Kafka／Redis／DB、volume 與 localhost 綁定，不等於多機 HA、TLS、正式備份或已完成安全掃描。沒有 rate limiter／WAF；限流也不能取代庫存原子性。
